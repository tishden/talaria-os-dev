POC-RESULTS §7. Файловая система получила **журнал JBD2 с барьерами**
(его воспроизводит и чужой e2fsck), дешёвый fsync (коалесинг + конвейер NVMe),
**файловый MAP_SHARED** через страницы блочного кэша и приватное адресное
пространство для `mode=cell`.

**Три оговорки, важные для следующего плана:**
- **Фаза «проверка §8 на настоящем EBS/NVMe» не выполнена**: пункты §8 закрыты
  по своим гейтам (локальный регресс, e2fsck, fsbench под QEMU), но на живом

  принимает AMI с `boot-mode uefi`. Нативный metal требует BIOS-загрузчика
  (или multiboot2+GRUB) — отдельная работа.
- **§7 гейт 1.5x не взят** (2.02x). Это не «почти», а честный остаток: см. выше.

**Достигнуто главное (сессия 2): Talaria загружается и работает на реальном EC2
без QEMU.** Цепочка на c6i.large: UEFI -> `uefi-stub` -> ядро -> PCIe -> ENA ->

## 8. [НОВОЕ, сессия 3] Файловая система: долговечность и цена fsync

Сегодня ext2 в Talaria — рабочая RW-ФС с write-back кэшем, но: (а) `fsync` любого
дескриптора = линейный проход по всем 2048 слотам кэша и **поблочная** синхронная
запись (одна NVMe-команда на 4 КБ, следующая — только после completion предыдущей),
(б) журнала нет — падение посреди обновления метаданных оставляет ФС на милость
`e2fsck`, (в) файловый `MAP_SHARED` отвечает `ENODEV` (нагрузки откатываются на
pread/pwrite), (г) `mode=cell` живёт в identity-пространстве ядра, а не в своём AS.
Это четыре разных дефекта одной подсистемы — блок закрывает их вместе.

- [x] **8.1 NVMe: PRP-списки, крупные передачи, конвейер** (сделано: PRP-список -> до 128 КБ одной командой, конвейер до QD-1 команд, MDTS учитывается): сейчас `rw()` шлёт
      максимум 4 КБ на команду (PRP1+PRP2) и ждёт completion каждой. Добавить
      PRP-список (страница указателей -> до 512 КБ на команду) и асинхронную
      подачу: `submit_async` в SQ без ожидания + `reap(n)` по phase-биту, глубина
      до QD-1 в полёте. Интерфейс `write_many(&[(lba, addr, nblk)])` для ФС.

      кратное ускорение групповой записи.
- [x] **8.2 ext2: список грязных блоков и коалесинг** (сделано: счётчик грязных + коалесинг в диапазоны; fsbench 512 блоков -> 2 диапазона, пустой fsync 4-6 мкс): вместо скана 2048 слотов —
      счётчик и битовая карта грязных (или связный список слотов); при сбросе

Бюджет AWS: план был < $150, **по факту потрачено ~$25** (c6a.metal ~1.6 ч и
m7i.metal-24xl ~1.2 ч — основное; десятки c6i.large-итераций и снапшоты —
копейки). Все ресурсы сессии 2026-08-25 зачищены (инстансы, AMI, снапшоты,
тома, ENI, SG, ключ); в аккаунте остались только посторонние ресурсы владельца.

Инструменты, появившиеся по ходу (пригодятся в следующей сессии):
- `infra/aws/ec2-boot-talaria.sh` — цикл «образ -> AMI -> инстанс -> serial-лог»
  за ~5 минут (dd на EBS-том builder'а -> снапшот -> register-image), без
  S3/import-snapshot. Нужен builder-инстанс с пустым томом /dev/sdf.
- `tools/mk-ami.sh` — GPT-образ (ESP с BOOTX64.EFI и talaria.cfg + раздел данных).
- `talaria.apcr4mask=0x..` — бисект битов CR4 на AP.
- Приём отладки драйверов: kprobe (bpftrace) на функции живого Linux-драйвера
  на таком же инстансе + побайтная сверка команд с нашими (так вскрылось
  требование Nitro к host_info).
