Design doc · a special-purpose OS for latency-critical workloads

Talaria OS

An operating system in which the application owns the hardware and the OS becomes the control plane. For trading, embedded systems and dedicated servers behind an external security perimeter. Talaria are the winged sandals of the messenger god: a layer that makes whoever puts it on fast.

1Summary

The whole practice of low-latency tuning of Linux — isolcpus, nohz_full, rcu_nocbs, mitigations=off, THP off, NUMA balancing off, busy-poll, kernel bypass, SCHED_FIFO — is a consistent switching off of the mechanisms of a general-purpose OS. For twenty years the HFT industry has been turning Linux into a unikernel by hand: the kernel is used as a bootloader and a control plane, while the data plane is assembled anew in user space on top of a dozen fragile boot parameters, sysctls and patches. Talaria turns that practice into a first-class system: what in Linux is achieved by tuning "against" the design is here the default model.

The core of the idea is four decisions, each of them proven either in research operating systems or in production:

  • Partitioning instead of time sharing. The machine is statically divided into a control plane (1–2 cores, where the whole "operating system" lives) and data cells — groups of cores owned exclusively by the application. On a cell's cores no OS code executes at all: no ticks, no IRQs, no kworkers. The pattern is proven by the HPC multi-kernels (McKernel/mOS), by Jailhouse and by the whole practice of core isolation in HFT.
  • A library kernel inside a cell. The application is linked with the OS runtime statically: the "syscalls" of the hot path are ordinary function calls (2–5 ns instead of 100–600 ns), there is a single address space and a run-to-completion reactor on every core (the Seastar/IX model). The rare cold syscalls are proxied to the control plane (the McKernel model).
  • I/O without a kernel as the only path. The native I/O ABI is queues in shared memory (the io_uring/Demikernel model): the NIC and NVMe queues are mapped straight into the application, the network stack is a library, TLS is a part of the transmit pipeline rather than a separate layer.
  • Compatibility through musl rather than through emulation. A POSIX subset (~200 Linux syscalls cover the server ecosystem) is implemented as a libc target: existing C/C++/Rust code is rebuilt without changes. Binary compatibility with Linux is a separate late mode, not a foundation.

The implementation language is Rust in the framekernel model (Asterinas): unsafe is isolated in a narrow framework, the rest of the system is safe code. The delivery channel of v1 is a KVM guest (virtio + VFIO passthrough of real NICs), which reduces the driver problem to one set of drivers and gives seconds to deploy and CI on ordinary machines; bare metal is the second phase.

The target niche by latency: a software wire-to-wire of 0.5–1.5 us and tail jitter an order of magnitude better than a tuned Linux. Below ~500 ns only an FPGA competes (the STAC-T0 record is 13.9 ns) — that is deliberately not our territory; ours is determinism, the p99.99 tails and the cost of ownership of the software path.

2Goals, non-goals, the threat model

2.1The goals

  • The jitter on a cell's cores: p99.99 < 1 us, the maximum < 5 us without manual tuning — "out of the box" better than a perfectly tuned Linux (p99.9 ≈ 4.9 us, max ≈ 18 us in the reference measurements).
  • The datapath's overhead: a "syscall" call = a function call; sending/receiving a packet through the native API — hundreds of cycles, zero copies, zero mode switches.
  • The footprint: a cell's image < 10 MB, a guest's boot < 100 ms, the full reproducibility of the build and of the configuration (the machine's passport as an artefact).
  • Compatibility: a server application in C/C++/Rust is rebuilt against musl "as is"; the toolchain, the debugger and the profiler are the standard ones (LLVM, ELF/DWARF, gdb, the PMU).
  • Observability as a first-class feature: the jitter counters, the tracing, the flight recorder and the crash dump do not degrade the hot path.
  • Two target ISAs in CI from day one: x86-64 and ARM64 (servers and embedded).

2.2The non-goals

  • A general-purpose multi-user OS, a desktop, the running of untrusted code, multi-tenancy.
  • Full POSIX and full binary compatibility with Linux (the chase after 100% of the ABI is endless; the experience of OSv).
  • A front end to an untrusted environment: the termination of external traffic, a DMZ, sandboxes. The external security perimeter is given by the problem's statement.
  • Records of minimal latency against an FPGA: the sub-100-ns path stays with the hardware, Talaria serves the software part and the management.
  • A full-blown general-purpose disk file system of our own: on the hot path there is an append log/blobstore, everything else is on the control plane.

2.3The threat model

A single trust domain: all the code on the machine is trusted, the environment is a colocation or one's own segment behind a firewall/bastion. Hence the architectural consequences that give "free" performance: the mitigations of speculative attacks are not needed (a return of 5–25% of the performance depending on the CPU's generation), seccomp/LSM/audit are absent as a class, ASLR is not needed (the determinism of the layout is a feature: reproducible profiles and cache behaviour). The MMU protection between the cells and the control plane is kept — but as a protection from bugs and as a debugging tool rather than from attacks; in a cell's release profile it is configurable. For development there exists a debug profile with full protection and sanitisers.

4The requirements from practice

The design was checked not on abstract scenarios but on a real problem of low-latency transport and on the industry's public data.

4.1The problem of low-latency transport (an HFT fund's challenge, DPDK/AF_XDP/FPGA)

A multi-backend transport of market data: shm rings without syscalls, kernel UDP vs AF_XDP vs DPDK vs lwIP-over-DPDK, FEC+NACK, an FPGA port of the protocol (an Alveo U50). The conclusions that matter for an OS: the system's limit is measured in packets per second, not in bytes; DPDK against kernel UDP at 500k msg/s — p50 12.4 vs 15.5 us, but p99.99 47.8 vs 105.5 us (a bypass wins the tails above all); the software part of the budget is 0.57 us out of ~12 (95% is the network and the environment); measurements without a PTP clock lie (chrony was wrong by 53.9 us while claiming 3.8); kernel patches were needed (write-combining for vfio-pci, the PHC in the ENA driver) — the very things the OS should have given itself.

4.2The industry

A software kernel bypass: Onload sockets ~1.5 us, TCPDirect 828 ns, a Solarflare X4 590 ns half-RTT, an ExaNIC raw 696 ns wire-to-wire. FPGAs: a full tick-to-trade of 100–500 ns, the STAC-T0 record is 13.9 ns. Nobody (by the public data) writes a custom OS — everyone uses a "gutted" Linux. That is exactly the market niche: to turn the standard practice into a system.

6Talaria's architecture

6.1The frame: the control plane and the data cells

At the boot the machine is statically divided by a manifest into a control plane (1–2 cores) and one or several data cells. The control plane is exactly the "operating system": the loading and the supervision of the cells, the drivers of the slow devices (virtio-blk, the console, the management network), the network management access (SSH/API), the telemetry and its export, the PTP daemon, the proxying of the cold syscalls, the gdb stub. A cell is a group of cores, ranges of memory and device queues owned exclusively by one application. On a cell's cores only the application and the runtime linked with it execute: interrupts are not routed there (except the explicitly requested ones), there are no ticks, there are no background OS threads, TLB shootdowns from foreign activity are impossible — there is no shared mutable memory map with the other cells.

6.2A cell: the manifest, the runtime, the execution

A cell is described by a declarative manifest (the configuration language is a descendant of Zephyr's Kconfig/devicetree): the cores, the volume and the layout of the memory (including the NUMA nodes and the page size), the devices and their queues, the channels to the other cells, the LLC/memory-bandwidth limits (Intel RDT / ARM MPAM), the polling policy. At the start the system guarantees the contract — rather than "checks and warns", as the self-diagnostics of a typical HFT application on Linux is forced to do: if a resource cannot be given out exclusively, the cell does not start.

Inside a cell there is the kernel-as-library model: a single address space, the runtime is linked statically, there is no user/kernel boundary. The execution is shard-per-core (Seastar): one reactor per core, run-to-completion with adaptive batching (IX), the shards communicate through explicit SPSC/MPSC rings, without shared locks. For workloads with mixed request durations (the server profile) a us-preemption is switched on: a dedicated dispatcher sends a timer IPI with a step of ~5 us (Shinjuku) — that is a manifest option, in the trading profile it is off. There are no blocking primitives on the hot path; the waiting is UMWAIT/TPAUSE on x86, WFE + an event stream on ARM: the latency of polling without burning the neighbours' turbo budget.

The cold operations (opening a configuration file, DNS, the exec of a helper process) are implemented by proxying onto the control plane through a ring of requests (the McKernel model): for the application that is an ordinary musl call which under the hood puts a request into a queue and yields the shard. The discipline "there are no syscalls on the hot path" stops being a convention — the hot calls are cheap by construction, the cold ones are explicitly asynchronous.

6.3The memory: static by default

  • All a cell's memory is given out at the start: hugepages of 2M/1G, prefaulted, pinned. There is no overcommit, no swap, no page cache on the data plane, no background compaction/migration/deduplication — by construction rather than by a setting. A page fault in a cell after the start is a bug, and the telemetry counts it as an error (the counter is bound to be zero).
  • NUMA is explicit: the manifest binds the ranges to the nodes; the allocators are per-shard, without global locks; the inter-shard handovers go by reference within a cell.
  • The partitioning of the LLC and of the memory bandwidth (Intel CAT/MBA, ARM MPAM) is a part of the manifest, a first-class API rather than resctrl magic.
  • The MMU is used minimally: an identity mapping of hugepages inside a cell (a minimum of TLB misses, no page walks on the hot path), the protection of the boundaries between the cells and the control plane. TLB shootdowns do not exist in the steady state — the memory maps do not change.

6.4I/O: queues as the only primitive

The native ABI is asynchronous queues in shared memory: submission/completion rings, buffers registered in advance, multishot operations. This is the io_uring model cleansed of its birth trauma: in a single trust domain there is no malicious neighbour, and "the kernel parses an SQE out of shared memory" stops being an attack surface. The application-level API is Demikernel's queue pairs (push/pop/wait_any), the same for the network, the storage and the inter-cell channels.

The network is three layers, all of them in a cell:

  • L0 raw: the NIC's queues mapped into the application (the ef_vi/DPDK model; in v1 — through a VFIO passthrough in a guest). Flow steering by the 5-tuple straight into a shard's queue. For the extreme cases there is a CTPIO-like transmit and a preloaded TX where the NIC can do it.
  • L1 lite stack: statically linked UDP/TCP (the base is smoltcp with SACK added, or a port of F-Stack for a full TCP), zero-copy, run-to-completion, without global state. On top of it there is a library of market-data primitives: a multicast join, an A/B arbitration by the sequence numbers, the detection of gaps, a snapshot recovery, FEC/NACK (the protocol and the code from §4.2 are reused directly). TLS is here too: the encryption is in the transmit pipeline (AES-NI/AVX, session resumption, readiness for a NIC offload) — a direct answer to the tens of microseconds of the TLS tax on the path "OpenSSL + a socket".
  • L2 compatibility: BSD sockets/epoll over L1 for code rebuilt without changes (the Onload model). The layer's price is measurable and documented (~2x against L1, as with Onload against TCPDirect).

The storage: a polled NVMe driver in a cell (the SPDK model), on top of it an append log/blobstore with ZNS on the horizon; there is no POSIX FS on the hot path. A full-blown file system (the configs, the logs, the artefacts) lives on the control plane; a cell writes there through the channels, the way HFT applications write logs through a cold thread. The hybrid polling of the NVMe (a sleep up to half the expected latency) is a manifest policy.

6.5The time

The primary clock is the invariant TSC (x86) / the generic timer (ARM): a read is single nanoseconds, without a syscall. The control plane calibrates and disciplines the clock (PTP/PHC on the NIC's hardware timestamps), publishing the coefficients in a shared page (the vDSO model) — the cells get the nanosecond UTC time by reading two cache lines. The API of the RX/TX hardware timestamps is a part of L0/L1. There is a built-in latency tracer: the application puts named checkpoints, the system glues them together with the NIC's timestamps and computes the percentiles and the σ outside the hot path. The guarantee of the TSC's migration safety is trivial: the threads do not migrate.

6.6The scheduling

On the data plane there is no classical scheduler: the core belongs to the shard, full stop. There is cooperative multitasking inside a shard (futures/a reactor) and an optional us-preemption (§6.2). The overload signal is the age of the queues' heads (Shenango): it is exported as a metric and, in the server profile, controls the donation of idling cores to batch cells (the Caladan mechanism, the MIT code as a reference). On the control plane there is an ordinary pre-emptive scheduler with priorities for the cold tasks; its quality is not critical.

6.7Security

It corresponds to the threat model of §2.3: the mitigations of speculative attacks are absent (there is no KPTI, no retpoline, no verw flushes — the syscall path and the switches get several times cheaper), there is no seccomp/LSM/audit/ASLR. The isolation is capabilities on the control plane (the seL4 model: a cell gets unforgeable rights to its own resources at the start and cannot reach foreign ones), MMU boundaries between the cells, an IOMMU for the DMA devices (a protection from an erroneous DMA, not from attacks; it can be switched off in the extreme trading profile with a measured price of the IOTLB). Secure/measured boot is an option for compliance. The debug build profile returns the full protection and the sanitisers — the development is done with the belts on, production flies without them.

6.8Compatibility and the ecosystem

  • libc: musl as the canonical target; static linking. musl's "syscalls" are the runtime's functions: ~200–224 calls of the Linux ABI cover the server ecosystem (Tsai et al.; Unikraft runs Redis/NGINX/Python with ~160). Three classes of implementation: the hot ones natively in a cell; the cold ones proxied to the control plane; the unsupported ones an explicit ENOSYS with a trace (the list is known at the linking stage).
  • The languages: C/C++ (a musl target, LLVM), Rust (a first-class target *-talaria), Go — later (the runtime requires futexes/signals — feasible, but not for v1).
  • Binary compatibility with Linux (running unmodified static ELFs) is a mode of the v3 phase: it is useful for adoption but is not a foundation (the lessons of OSv: the chase after the full ABI is endless; a runtime translation is ~10x dearer than linking).
  • The formats and the debugging: ELF, DWARF, a gdb remote stub through the control plane (a cell is debugged not from its own cores), a perf-like access to the PMU, symbolised crash dumps.
  • The export of the observability: OpenTelemetry/Prometheus from the control plane; the trace formats are open (perfetto-compatible).
  • The boot: x86-64 — UEFI + the Linux boot protocol/PVH (bootability by any VMM and by GRUB "for free"); ARM64 — SystemReady (servers: UEFI+ACPI+PSCI) and a devicetree (embedded).

6.9The drivers and the platforms

The driver chasm is the main killer of new operating systems; the strategy is to minimise it structurally:

  • v1 — a KVM guest (Cloud Hypervisor / Firecracker / QEMU): virtio-net/blk/console/vsock (modern-only, a packed ring) + a VFIO passthrough of the latency-critical NICs. The PMDs of the physical NICs (mlx5, ice, the ef_vi class) live in a cell as libraries — by the DPDK model, where the driver is in user space anyway; the references and part of the code are reused. The Rust crate virtio-drivers closes virtio at little cost. The hypervisor here is not a virtualisation layer in the usual sense but a tool for booting and for compatibility with foreign hardware; a guest's jitter tax is measured and published.
  • v2 — bare-metal x86-64: UEFI, ACPI, NVMe, with the same PMD model; the choice of the reference hardware with control over the SMI (that is a procurement requirement, not a software one).
  • v3 — ARM64: SystemReady servers (the Graviton class, Ampere), embedded boards through a devicetree + PSCI; the DPDK ecosystem on ARM is tier-1, the PMDs are portable.
  • The clouds (on demand): the ENA/gVNIC/MANA drivers — the big three are not virtio; the NVMe driver is reused everywhere.

6.10Observability: the anti-lesson of the unikernels

The unikernels died not from a lack of speed but from undebuggability in production. So:

  • Always-on counters of the perturbations at zero price on the hot path (increments in per-shard cache lines): page faults (bound to be 0), pre-emptions/IPIs (bound to be 0 in the trading profile), the depth and the age of the queues, the PMU (LLC/TLB misses, the IPC). A violation of an invariant is an alert, not a line in a log.
  • A flight recorder: a ring trace of the runtime's events and of the application's checkpoints in shared memory, read from the control plane without stopping the cell; after a failure it survives and enters the crash dump.
  • A crash dump of a cell (the memory + the registers + the flight recorder) onto the control plane; the DWARF symbolisation is offline.
  • A gdb stub and a "ps/top/netstat equivalent" — the control plane's CLI, showing the shards, the queues, the counters, the channels.
  • The machine's passport: the full configuration (the manifests, the versions, the topology, the microcode, the CPU's flags) is one reproducible artefact, automatically attached to the telemetry and to the benchmarks (the practice from §4.2 raised into a system).

6.11The implementation and the reuse

  • The language: Rust, the framekernel architecture (Asterinas): unsafe is only in an isolated framework (the pages, the MMIO, the interrupts), the whole of the logic is safe. C code is admitted in the borrowed PMDs/stacks behind an FFI boundary. The justification of the choice against C++ is in §6.12.
  • What we reuse (all the licences are permissive): musl (MIT); smoltcp (0BSD) as the base of L1; the F-Stack/FreeBSD stack (BSD) as an option for a full TCP; the ideas and the code of Shenango/Caladan (MIT) for the donation of cores; virtio-drivers (MIT); DPDK/SPDK (BSD) as a reference for the PMDs and for the polled NVMe; the rust-osdev crates (bootloader, x86_64, aarch64); the LLVM/rustc toolchain; FEC/NACK/the arbitration — from the code base of §4.2.
  • What we do not write: a compiler of our own, a general-purpose disk FS of our own, a TLS primitive of our own (we use ring/aws-lc behind a narrow interface), drivers for the whole zoo of hardware.

6.12Why Rust and not a modern C++

The choice of the kernel's language here is a part of the architecture rather than a matter of taste. Talaria is a single address space, a library kernel, a minimum of MMU, without a user/kernel boundary: we have deliberately traded the hardware protection for performance. In such a system a dangling pointer or a data race is not a segfault with a core dump but a quiet corruption of the state in ring 0. Linux can afford C, because the MMU insures at least user space; a unikernel-like system cannot. The compiler is bound to compensate for the protection — statically and for free at runtime. Theseus and Asterinas are built directly on that thesis: isolation by means of the type system instead of isolation by means of the MMU. The C++ sanitisers are not an equivalent here: they work in a debug build, while UB in release keeps silent.

The second argument is concurrency in the type system. Shard-per-core, SPSC rings, seqlocks, pages shared between the cells and the control plane — the whole inter-shard contract ("what may be passed between cores") is encoded in Rust by Send/Sync, and a data race becomes a compilation error. In C++ that class of contracts is held by conventions and by review (a typical symptom: TSan does not understand a custom SPSC Disruptor, and the project lives with a suppression file). The third is auditability: in the framekernel model all the unsafe is concentrated in a framework of a few thousand lines, which can be read line by line; in C++ the "unsafe surface" is the whole code base.

The honest counter-arguments for C++: template metaprogramming is more powerful (NTTPs, variadics, constexpr-everything — const generics in Rust are still limited); the team's expertise is C++, and the speed of development in C++ in the first year would have been higher; the borrow checker in lock-free and self-referential structures is a real pain, and part of such code will be unsafe anyway. The mitigating circumstances: the kernel is new code in any case, the applications stay in C++ and are linked through musl/the C ABI — the kernel's language is not imposed on the application; for the osdev niche Rust's ecosystem is richer today (the no_std crates bootloader/x86_64/aarch64/virtio-drivers/smoltcp are ready-made proven bricks); and "modern C++" in a kernel is cut down anyway — the exceptions and the RTTI are switched off (latency-oriented C++ is built with -fno-exceptions as it is), strict aliasing is a minefield for code that casts network buffers, while Safe-C++/profiles are a horizon of years away.

The decision: the kernel and the framework are Rust; the PMDs, the codecs and the borrowed stacks are C/C++ behind an FFI boundary without restrictions; the applications are in any language against musl, and C++ stays first-class. If Talaria were a monolith with an MMU boundary, the team factor would have outweighed in favour of C++; in a system without hardware protection C++ does not have the needed tool, however many templates we might write.

7Three profiles out of one code base

A profile is a preset of the manifest and of the composition of the libraries, not a fork:

  • trading: the maximum of determinism — poll-only, preemption off, the IOMMU optionally off, the L0/L1 network, the TLS pipeline, the market-data primitives, PTP. One or two hosts, a colocation.
  • server (behind an external perimeter): mixed workloads — a us-preemption, the donation of cores to batch cells, L2 sockets for rebuilt applications, a polled NVMe + a blobstore, an OTel export.
  • embedded: a small footprint — one image per board, a devicetree, static-everything, an option without an MMU; the L1 stack in an lwIP-class configuration; a candidate for seL4 as a certifiable foundation of mixed criticality.

9The risks and the open questions

  • "Linux will catch up". io_uring, AF_XDP, EEVDF and PREEMPT_RT-in-mainline narrow the gap. The answer: the gap in the tails and in the determinism is structural (a shared kernel, the mitigations, the background housekeeping are ineradicable), while the operational price of tuning Linux is constant. The metrics of §8 are compared exactly against a tuned Linux; if the gap disappears, the project is not needed, and that is checkable on v0.
  • An FPGA from below. The sub-500-ns path goes into the hardware. The answer: Talaria is positioned as a host system around an FPGA (the host plane, the doorbell models, the telemetry — §4.2 shows that the PCIe host path is exactly the bottleneck, and one has to own it), not as a competitor.
  • The driver chasm. It is mitigated by the v1 strategy (virtio + VFIO + the PMD model), but the bare-metal zoo stays a limitation: we support a short list of reference hardware, and that is a product decision.
  • The ecosystem and the trust. A new OS without operators, documentation and success stories. The answer: first-class observability (§6.10), musl compatibility (a low cost of entry), and the first beacon workload is a real trading platform (§4.1) as a reference port.
  • Rust in a kernel is already harder to hire for than C. Acceptable: the team is small by design, while a safe kernel radically lowers the cost of the bugs that are fatal in a single-address-space system.
  • The open questions: the manifest's format (a DSL of our own vs a superset of the devicetree); the full TCP — an improved smoltcp or a port of the FreeBSD stack; is a us-preemption needed in v1 or only in the server phase; the model of a hot update of the cells (a restart with a handover of the state vs a Theseus-like live replacement); the project's licence.

10The roadmap

  1. v0 — the PoC (one quarter): a Cloud Hypervisor guest, one cell + a mini control plane, virtio-net, a reactor, a TSC clock, the counters. The benchmark: a UDP echo against a tuned Linux/io_uring and against DPDK on the same host. The gate: the gap in the tails is confirmed — otherwise the project stops.
  2. v1 — the trading kernel: a VFIO NIC + a PMD (mlx5 or an ef_vi-class one), the L1 stack + mcast/the A/B arbitration + the TLS pipeline, PTP, a flight recorder, a gdb stub, a musl target. The beacon: a port of the feed handler and of the order gateway of a real platform (§4.1); a comparison of the tick-to-trade with its current production.
  3. v2 — bare-metal x86 + the storage: a UEFI boot on the reference hardware, a polled NVMe + an append store, the donation of cores, the server profile.
  4. v3 — ARM64 + embedded + compatibility: a SystemReady server and one embedded board, a devicetree, a profile without an MMU; the mode of running static Linux ELFs.
